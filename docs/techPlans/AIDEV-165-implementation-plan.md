# Implementation Plan: AIDEV-165

## Effort & Risk Analysis
*   **Complexity (T-Shirt):** S
*   **Estimated Effort:** 1-2 days for the bootstrap change, followed by a separately reviewed AIDEV-157 rebase and full review
*   **Primary Risk:** Review-workspace provisioning could read candidate-controlled `delivery.review` values, or turn an absent trusted policy into a generic configuration error that is accidentally bypassed. The bootstrap must bind policy bytes and the preflight executable to the immutable trusted base before any candidate profile is consulted, while preserving an explicit legacy-base `bootstrap_required` result.

This is a bootstrap-only change. The regression target is the AIDEV-157 pre-feature base `aee0f2e6244aedc85fd1fc8620af317aeeb8f284`; the first reviewable AIDEV-157 base is the exact merge commit of this bootstrap implementation. This change does not implement AIDEV-157's clone, lease, quarantine, or cleanup mechanics, and it does not merge AIDEV-157.

## Step-by-Step Execution
1.  **Phase 1: Freeze the trusted policy contract**
    *   Step 1.1: Add `delivery.review` as an optional structural property only for legacy-schema compatibility. Define the exact nested shape: `workspaceRoot`, `quarantineRoot`, `remotePolicy`, `quarantineRetentionSeconds`, and `limits` containing `maxWorkspaces`, `maxWorkspaceBytes`, `maxQuarantineBytes`, `maxUntrackedEntries`, and `maxUntrackedBytes`. Set `additionalProperties: false` at the review object and `limits` object, and make every ready-policy field required by the runtime validator. Enforce exact semantic ranges: retention `0..31536000` seconds; workspaces `1..256`; workspace and quarantine bytes `1048576..8589934592` each; untracked entries `1..100000`; and untracked bytes `0..2147483648`.
    *   Step 1.2: Use these exact approved values for the active Pi Sampler policy: workspace root `../ai-workspaces/review`; quarantine root `../ai-workspaces/review-quarantine`; no publication remote; 86,400-second retention; maximum 16 active workspaces; 2,147,483,648 bytes each for workspaces and quarantine; at most 512 untracked entries; and at most 536,870,912 untracked bytes. Roots resolve outside the repository, are distinct and non-nested, and are not created by policy loading.
    *   Step 1.3: Define root syntax precisely: the approved `../ai-workspaces/...` form is the one permitted parent-root escape from the repository; reject additional parent segments, dot or empty segments, duplicate separators, absolute/drive/UNC forms, and any resolved root that remains inside the repository. Compare normalized roots with Windows case-folding, reject equal/nested aliases, and reject existing symlink/junction/reparse ancestors without creating missing directories.
    *   Step 1.4: Keep the policy declarative and consumer-owned: do not add credentials, lease tokens, reviewer identity, absolute machine paths, mutable branch names, external URLs, or a new trust root. Keep the optional `governance/.pi/policy.json` package/model policy separate.
2.  **Phase 2: Implement a trusted-base-only preflight**
    *   Step 2.1: Define `loadTrustedReviewPolicy({ repo, mode, baseSha, candidateSha })` and a `verify` CLI in `scripts/review-policy.mjs`. The profile path is a module constant exactly equal to `profiles/pi-sampler.json`; there is no caller or CLI override. `mode: "bootstrap-check"` may omit `candidateSha` and can report only policy presence; `mode: "review-preflight"` requires an exact `candidateSha` and is the only mode allowed to return `status: "ready"`; every other mode is rejected as `mode_invalid`. Reject refs, tags, short SHAs, non-commit objects, candidate-selected repository/loader paths, and wrong base-to-candidate ancestry.
    *   Step 2.2: Bind execution provenance to the approved merged base: invoke the preflight executable from the clean checkout of that trusted base, resolve the base to the exact 40/64-character commit supplied by the trusted review controller, verify repository identity and ancestry to the candidate, and record that base SHA in the result. Do not execute a loader or read policy defaults from the candidate checkout. A `review-preflight` result without `candidateSha` is invalid and cannot authorize review; a `bootstrap-check` result is never an authorization result.
    *   Step 2.3: Read both the fixed `profiles/pi-sampler.json` and fixed `profiles/project-profile.schema.json` from the trusted base Git object database. Compile that trusted JSON Schema with the repository's existing `Compile` entry point from `typebox/compile`, expose `validateTrustedReviewProfile` for semantic readiness, and make the runtime validator use the same schema bytes rather than a candidate or duplicated ad hoc schema. Tests must run both against the same base fixtures and assert parity for unknown fields, missing nested limits, and invalid values. The optional schema property is intentional only so the old base can reach the explicit bootstrap classification before ready-policy validation.
    *   Step 2.4: Run every Git child process through a bounded streaming wrapper: allowlist only `PATH` and required platform process/temp variables; set `GIT_TERMINAL_PROMPT=0`, `GIT_CONFIG_NOSYSTEM=1`, `GIT_CONFIG_GLOBAL` and `GIT_CONFIG_SYSTEM` to the platform null device, and remove inherited `GIT_*` variables. Invoke `git --no-replace-objects` with hooks, external diff, and text conversion disabled. Cap stdout at 131073 bytes and stderr at 16384 bytes, terminate the child on overflow, and return a bounded code without retaining unbounded output.
    *   Step 2.5: Validate a real repository root and commit/blob object from the immutable base. Reject shallow repositories, graft files, replacement refs, alternates files or alternate-object environment, and object IDs that resolve outside the trusted object database. Require the exact base and candidate commits to be full IDs and verify ancestry with replacement objects disabled; do not write files or resolve/create candidate-controlled directories.
    *   Step 2.6: Parse each Git blob with a pre-parse byte cap of 131072 bytes, maximum depth 16, maximum object keys 128 per object, maximum array items 128, maximum string length 4096 UTF-8 bytes, maximum total nodes 1024, duplicate-key rejection, and safe-integer-only numeric handling. Use a bounded duplicate-aware parser rather than native `JSON.parse` alone. Return bounded constant messages without raw profile content, absolute paths, environment values, or Git stderr.
    *   Step 2.7: Use a two-stage decision: first parse the trusted base profile enough to determine whether it is syntactically valid and contains a `delivery.review` object; if that object is absent, return the blocked result below before full ready-policy validation or any candidate read. Only a present review object proceeds to trusted schema validation, semantic validation, root relationship checks, and candidate-profile equivalence.
    *   Step 2.8: Define the stable result envelope as `format: "pi-sampler.delivery-review-policy"`, `version: 1`, `mode`, `status: "bootstrap_only" | "ready" | "blocked"`, `code: "policy_present" | "ready" | "bootstrap_required" | "base_invalid" | "policy_invalid" | "candidate_required" | "candidate_invalid" | "profile_drift" | "mode_invalid" | "git_output_oversized" | "internal_blocked"`, exact `baseSha`, fixed `profilePath: "profiles/pi-sampler.json"`, and optional `candidateSha`. `bootstrap-check` returns `bootstrap_only/policy_present` or blocked `bootstrap_required`; `review-preflight` returns `ready` only when `mode`, exact `candidateSha`, trusted schema/runtime validation, ancestry, root checks, and candidate policy/profile equivalence all pass. The loader rejects unknown modes and the outer error boundary maps every unexpected parser, Git, filesystem, or dependency error to a bounded `blocked/internal_blocked` result; no unclassified exception can produce `ready`. A ready result includes the validated policy, `policyDigest`, and `bindingDigest`; a blocked result includes no policy values. The CLI exits zero only for `code: "ready"` and exits nonzero for every other code, including `bootstrap_required`.
    *   Step 2.9: Define digests exactly: `policyDigest` is SHA-256 of the UTF-8 bytes of the compact canonical JSON for the `delivery.review` object only; `bindingDigest` is SHA-256 of the UTF-8 bytes of the compact canonical JSON for `{format, version, mode, baseSha, candidateSha: candidateSha ?? null, profilePath, policyDigest}`. Canonical JSON recursively sorts object keys by code-unit order, preserves array order, uses JSON-standard escaping and safe integer decimal forms, has no whitespace, and has no trailing newline. The digests bind the exact candidate authorization, policy bytes, base, and path for integrity and repeatability; they do not independently prove maintainer authority.
3.  **Phase 3: Document and regression-test the bootstrap boundary**
    *   Step 3.1: Document the two-step landing order: merge this bootstrap change first; record its exact merge SHA; require the later AIDEV-157 review controller to invoke the preflight executable from that trusted base with that SHA and a mandatory candidate SHA; then require AIDEV-157's candidate policy/profile bytes to match the trusted policy before workspace preparation. A base lacking the policy is a blocking `bootstrap_required` result, not an unexpected configuration failure.
    *   Step 3.2: Add a regression bound to `aee0f2e6244aedc85fd1fc8620af317aeeb8f284`. Assert that `bootstrap-check` and `review-preflight` with a divergent candidate both return `status: "blocked"`, `code: "bootstrap_required"` before candidate inspection, and no candidate-controlled root, workspace, lease, or filesystem artifact is created. If the historical Git object is unavailable, fail with an actionable fixture/setup error; do not silently skip the required regression.
    *   Step 3.3: Add deterministic temporary Git-object fixtures for success and attack cases: create immutable pre-bootstrap and post-bootstrap commits through Git plumbing, invoke the loader with exact commit IDs rather than a working-tree file, and ensure the post-bootstrap fixture contains the approved nested policy. Add a candidate commit with divergent roots/remote/limits and assert that a ready base produces `profile_drift` without adopting candidate values; assert that omitting `candidateSha` produces `candidate_required`, never `ready`.
    *   Step 3.4: Add malformed, oversized, deeply nested, duplicate-key, unsafe-number, invalid-object-type, invalid-base, short/ref-SHA, profile-path injection, hostile Git environment/config, shallow/graft/replacement/alternate-object, symlink/junction/reparse ancestor, root-overlap, nested-root, case-alias, drive/UNC, and child-output-overflow cases. Reject Windows device-name segments (`CON`, `PRN`, `AUX`, `NUL`, `COM1`-`COM9`, `LPT1`-`LPT9`) case-insensitively, trailing dot/space segments, colons/alternate data streams, control characters, and wildcard/reserved separators. Assert bounded nonzero results, redacted stable codes, no writes, no candidate directory resolution, and a concrete import-DAG check: `review-policy.mjs` may import only approved `node:*`/schema-validation dependencies, while any later `review-workspace.mjs` may depend on preflight but preflight must never import it.
4.  **Phase 4: Handoff without implementing AIDEV-157**
    *   Step 4.1: Run only the profile's declared verification command and confirm the planning/implementation inventory contains no AIDEV-157 runtime or merge changes. The AIDEV-157 candidate must drop or become a no-op for its overlapping profile/schema edits after rebasing; it must not replace the trusted policy with candidate-controlled values.
    *   Step 4.2: After this bootstrap implementation is merged, rebase AIDEV-157 onto its exact merge commit, invoke `review-preflight` from the trusted bootstrap base with both exact base/head IDs, make its review-workspace entrypoint consume only the ready result and the nested `delivery.review.limits` contract, require exact-head isolated-workspace tests to pass, and obtain a fresh independent review. No AIDEV-157 implementation, publication, tracker transition, or merge is performed by this plan.
